# Business need to user story

1. Ground the work in the current working directory: read project instructions and relevant docs, code, and tests. Use the project to understand terminology and existing behavior, not to guess product intent. Do not edit project files.
2. Identify uncertainties that could change the actor, outcome, scope, permissions, edge cases, or acceptance criteria. Resolve what you can from project evidence; ask focused questions for the rest. Ask follow-ups as needed and do not finalize the story while material questions remain unanswered.
3. Once clear, present:
   - **Context:** relevant project facts.
   - **User story:** “As a …, I want …, so that …”. Do not invent the persona or outcome.
   - **Acceptance criteria:** uniquely numbered, observable, and pass/fail testable; use Given/When/Then where useful.
   - **Scope / non-goals** and **assumptions**, only where they clarify the request.

If there is no identifiable project context, ask which project to use. Output the story in the conversation; save it only if asked.
